# 1.0.1+26.2 — the bot no longer freezes while collecting food

Made for **Minecraft 26.2** (Fabric, Java 25). A patch release for the one thing reported after
1.0.0: **the bot stopping dead while it is collecting food**, most often described as "it stops
moving when it needs to pick up an item". Reported as Issue #2 against 26.3 (`@gamer` and
`@selfcare`, singleplayer); this branch carries the same code and the same fix.

Nothing else changed. There is no new content, no new command and no settings change.

---

## What was happening

`@selfcare` (and `@gamer`) start by collecting food, and the freeze happened in that phase: the
bot would walk to a village, break a hay bale or a crop, pick something up, and then stand perfectly
still — no aim, no swing, no movement — while the debug chain showed it was still working on a
pickup.

Reproduced on a live 26.3 client (same code) in a village world:

- the bot broke a hay bale and collected **one** hay block;
- a **second** hay block drop was lying on the ground six blocks away;
- the task chain read `<Pickup Dropped Items: [[hay_block]]> Collected.`;
- the body stood at **(-276.3, 69.0, -236.1) for five minutes**, and only the drop despawning
  ended it.

That is the whole bug. It is not slow pickup and it is not pathfinding: the task believed it was
finished with a drop it had never collected, and the parent kept handing it back.

## Why

1.0.0 taught the pickup task to stop Baritone the moment the stack was in the pack ("the inventory
is the truth, not Baritone's follow process"). The intent was right; the completion condition was
missing. `PickupDroppedItemTask` inherits `isFinished()` from `AbstractDoToClosestObjectTask`,
which is `false` for ever — completion was always the *parent's* inventory check. That is fine for
a `ResourceTask`, and wrong for `CollectFoodTask` / `CollectMeatTask`, which ask
`currentResourceTask.isFinished()` to decide when to move on.

The second half is the target count. Those two tasks built the pickup from the drop, but asked for
**one** of the item regardless of what was already held. With one hay block in the pack, the new task
was satisfied on its first tick: the Baritone branch below saw the inventory target met, printed
`Collected.`, cancelled the follow process and returned — having collected nothing. Every ten
seconds the food task's option timer rebuilt the same already-satisfied pickup because a matching
drop was still on the ground, so the freeze repaired itself into a loop.

The same shape exists for meat (`CollectMeatTask`) and for every item in `CollectFoodTask`'s
pickup list, so this was reachable from any animal kill or crop break — which is why the report says
"almost always when it tries to pick up an item".

## The fixes

- **A pickup task is finished when its items are in the pack.**
  `PickupDroppedItemTask.isFinished()` now returns
  `StorageHelper.itemTargetsMetInventoryNoCursor(itemTargets)`. Parents that ask get a true answer,
  and the Baritone follow process is still cancelled on the same tick.
- **Food and meat pickups ask for what the bot holds plus the drop** (`held + 1`), so the task is
  never born satisfied. This is the same "count is absolute, not relative" class of bug the 1.0.0
  crafting fix addressed in `CraftInTableTask`.
- **A Baritone pickup now has a give-up clock.** `IFollowProcess.pickup` will not always reach a
  drop — it can be inside a block, on a ledge its planner refuses, or the follow process can fail to
  take control. 1.0.0 trusted it and returned `null` every tick with no progress check, which is
  the other way the bot stands still "picking something up". The pickup now tracks the drop's best
  distance and, after **30 s without closing**, declares that drop unreachable, excludes it
  (`EntityTracker.requestEntityUnreachableNow` — one decisive exclusion rather than four slow
  failures), stops the follow process and lets the parent pick another drop or another job.
  Counter: `baritonePickupGaveUp`.
- Nothing else: no timing, no movement and no combat behaviour was touched.

Files changed (`PickupDroppedItemTask`, `CollectFoodTask`, `CollectMeatTask`, `EntityTracker`
for the decisive exclusion helper).

## Verification

The deterministic case was reproduced on a live client (26.3 build of the same code), and fixed with
this change: with one hay block in the pack and a hay block drop summon three blocks away, the drop
was collected (pack 1 → 2) and the food task continued with wheat and carrots — no `Collected.`
standstill. Normal `@food 220` gathering kept moving and picking up drops. The give-up clock was
seen firing only on a mutton drop Baritone could not reach
(`Baritone pickup stopped closing on item.minecraft.mutton (30s) — dropping that drop.`), after
which the bot went back to killing cows instead of waiting.

Both branch jars are built from the same fix; the 26.3 jar and its live verification are in the
main-branch release.
